# v1.1 Compatibility, Architecture, and Multilingual Diagnostics Design

## Status

Approved design for the sequential `A -> D -> B` implementation:

1. DeepSeek Harness compatibility automation;
2. targeted Module deepening;
3. multilingual and higher-leverage diagnostics.

This design targets `dsh-request-flight-recorder` 1.1.0. It preserves the v1
reader protocol, record schema, privacy model, bounded memory, and passive
Agent Loop behavior.

## Goals

- Detect new DeepSeek Harness release candidates and prove compatibility
  through static, installation, startup, and real Agent Loop evidence.
- Concentrate recorder transactions and Harness-specific knowledge in deep
  Modules before adding user-facing behavior.
- Render `/flight` descriptions, hints, output, and errors in the user's
  current DSH language.
- Support Chinese and English with complete dictionaries and Chinese fallback.
- Add bounded Session-scoped filters, explanations, and retained-window
  statistics without collecting new record fields.

## Non-Goals

- Modifying Agent Loop inputs, Prompt semantics, stream chunks, ordering,
  backpressure, cancellation, return values, or exception identity.
- Retaining message bodies, Prompt text, tool descriptions, arguments,
  results, variable values, credentials, raw provider responses, or raw error
  messages.
- Persisting or exporting flight records.
- Inferring language from message content, model output, operating-system
  locale, or environment variables.
- Supporting languages other than `zh` and `en` in 1.1.
- Adding a diagnostics UI. The Client Half only synchronizes the initial
  language preference.
- Changing `FlightRecorderReader`,
  `FLIGHT_RECORDER_PROTOCOL_VERSION`, or
  `FLIGHT_RECORD_SCHEMA_VERSION`.

## Invariants

The following remain release blockers:

- The plugin is a passive observer.
- Records are process-local, immutable, content-free, and bounded.
- The Ring Buffer defaults to 128 records.
- `/flight` output remains at most 4 KiB.
- Commands remain Session-scoped.
- Unknown or malformed language values fall back to Chinese.
- Formatting and language changes do not advance recorder revision or health
  counters.
- A new DSH version is unsupported until its complete compatibility gate
  passes and package metadata explicitly declares it.

## Delivery Order

The work is delivered in three independently verifiable phases. A later phase
does not begin until the previous phase is green.

```text
A: compatibility evidence
  -> D: deep recorder and Harness Modules
  -> B: multilingual diagnostics
```

This order keeps upstream compatibility failures separate from internal
refactors and user-facing behavior.

## A. DeepSeek Harness Compatibility Automation

### Supported-Version Policy

The package continues to declare exact DSH release-candidate peer versions.
Compatibility is evidence-based, not inferred from SemVer ranges.

- The currently supported RC is blocking in CI.
- A newly discovered `latest` or `next` RC starts as observational.
- Passing observational checks does not widen package metadata automatically.
- Supporting a new RC requires an explicit reviewed change to peer
  dependencies, compatibility documentation, generated output, and release
  evidence.
- Verification-only improvements may ship as a patch. Adding support for a new
  DSH RC ships as a minor version.

### Static Contract Gate

For each candidate DSH version:

- install exact public npm packages without workspace links;
- compile against Cordis, Agent, Brand, Commands, Invariants, LLM, Session,
  Settings, Client Locale, and System Prompt contracts;
- verify official event payloads and the Agent Loop marker;
- verify the Bundle patch composes exactly one
  `request-flight-recorder` row;
- verify package peer versions and documentation agree.

Type compatibility alone is insufficient to claim support.

### Isolated Installation Gate

The gate creates a temporary `DSH_HOME` and never reads or modifies
`~/.dsh`.

It must:

1. install the exact public `@deepseek-ai/dsh` candidate;
2. install the packed recorder artifact through the official plugin command;
3. dump the composed Profile;
4. start the Profile on an ephemeral port;
5. verify clean startup and module resolution;
6. stop and restart the Profile;
7. remove the temporary home.

The test must not resolve DSH packages from a sibling source checkout.

### Real Agent Loop Gate

The gate uses the official DSH local Mock LLM and no provider credentials. It
performs two requests in one Session and verifies:

- one capture and one completion per request;
- exact Turn, Step, and Attempt coordinates;
- `latest`, `list`, `show`, `diff`, and `health`;
- Session isolation;
- no correlation misses, projection failures, or unexpected truncation;
- process-local records and health reset after restart;
- no prompt, message, model-response, variable-value, or Mock-key canary in
  recorder output.

### Discovery Workflow

A scheduled GitHub workflow queries npm `latest` and `next` daily.

- No new RC: report success without repository writes.
- New RC: run the observational matrix and publish a workflow summary.
- Compatible candidate: report that a reviewed support change may begin.
- Incompatible candidate: identify the first failed layer: install, compile,
  compose, boot, Agent Loop, command, privacy, or cleanup.

The workflow must not create commits, tags, releases, or dependency updates.

## D. Targeted Module Deepening

### Recorder State Module

Introduce one transaction-oriented Recorder State Module behind a small
internal Interface. Its Implementation owns:

- `FlightRingStore`;
- active request identities;
- captured, completed, evicted, truncated, correlation, projection, and
  subscriber counters;
- revision advancement and saturation;
- `FlightSubscriptions`;
- atomic snapshots;
- first terminal settlement;
- disposal and zero-state reset.

Its transaction semantics remain:

- insertion and simultaneous eviction advance revision once;
- first terminal settlement advances revision once;
- duplicate settlement is ignored;
- a correlation miss or projection failure advances revision once;
- subscriber failure does not recursively advance revision;
- reads never advance revision.

`RequestFlightRecorder` retains the public Reader Interface but delegates state
operations to this Module. Tests exercise its Interface rather than casting
through private fields.

### Harness Capture Adapter

Deepen the Harness Capture Adapter so its Implementation owns:

- registration of the three official Harness events;
- Agent Loop marker filtering;
- Prompt Assembly and pending-request correlation state;
- strict Signal, Agent identity, and Session matching;
- structural projection and projection-failure isolation;
- downstream invocation and stream observation;
- disposal guards for asynchronous continuations.

The Adapter submits domain transactions to Recorder State. Recorder State does
not know DSH event payload shapes.

This is the primary adaptation point for future RC changes. Adapter tests use
official event sequences and prove downstream stream, Chunk, error, return,
throw, cancellation, and backpressure transparency.

DSH `FinishReason` values `aborted` and `error` contain an `LlmFailure`,
including a raw human-readable message and provider request ID. The Adapter
must never copy that object into a flight record. It normalizes either kind to
the existing privacy-safe terminal outcome:

```ts
{
  kind: 'threw',
  error: { kind: 'error' },
  firstChunkMs,
  totalMs,
  usage,
}
```

The original Finish Chunk still passes downstream by identity. This changes
only the recorder's terminal classification, keeps the v1 Schema shape, and
closes the raw-failure retention path.

### Snapshot Command Module

Remove the single-implementation `FlightDiagnostics` Interface. The Command
Module consumes the stable `FlightRecorderReader` Interface.

Each command execution:

1. resolves the current locale;
2. reads one Session-scoped atomic Snapshot;
3. parses and resolves identifiers inside that Snapshot revision;
4. computes output without another recorder read;
5. localizes and bounds the result.

`latest`, `list`, `show`, and `diff` therefore cannot observe different
revisions during one command. The prior artificial
"evicted between prefix resolution and rendering" behavior is replaced by
atomic Snapshot semantics and documented as a deliberate internal behavior
improvement.

### Explicitly Rejected Refactors

- Do not split `project.ts` into request, Prompt, Tool, and Message Modules.
  Its current Interface already hides privacy filtering, limits, cycle
  detection, and omission accounting.
- Do not split `types.ts` by type category. Public protocol locality is more
  valuable than smaller files.
- Move internal stream-observation types out of the public protocol area only
  when it reduces accidental exposure without changing root exports.
- Do not add seams for UUIDs, clocks, stores, formatters, or individual
  subcommands while only one production Adapter exists.

## B. Multilingual and Higher-Leverage Diagnostics

### Language Contract

Version 1.1 supports exactly:

```ts
type FlightLocale = 'zh' | 'en'
```

Resolution order is:

1. persisted DSH Host `locale.preference`;
2. browser language detected by the DSH `LocaleRuntime` and synchronized on
   first use;
3. Chinese fallback.

Unknown, absent, or malformed values resolve to `zh`.

The plugin never infers language from user prompts or model output and never
uses Node's machine locale as a Host fallback.

### Minimal Client Half

The public DSH locale currently keeps browser detection as a provisional
Client value and does not persist it automatically. A minimal Client Half is
therefore required to satisfy the approved resolution order.

The Client Half:

- injects the existing DSH locale and settings-scope Client Interfaces;
- observes the active `zh` or `en` locale;
- checks whether Host `locale.preference` is absent;
- writes the detected locale once when absent;
- performs no write when an explicit preference already exists;
- performs no diagnostics rendering;
- does not access Sessions, flight records, prompts, messages, or credentials;
- disposes all listeners through Cordis effects.

It runs when the Web Client plugin starts. Immediately before writing, it
re-reads the Host preference. If another tab has committed a preference, that
value wins. A conflicting write is not retried, so a later-starting tab cannot
overwrite the first committed preference.

Subsequent language changes continue through DSH's native language setting.
The Client Half does not create a second preference UI.

### Host Locale Module

Add a small, deep Host Locale Module that:

- optionally injects the DSH Settings Interface;
- reads the registered `locale` namespace at command execution time;
- normalizes only `zh` and `en`;
- falls back to `zh` if Settings is absent or invalid;
- captures the startup locale for static command metadata.

Command result output changes on the next execution after a DSH language
change. The command description and input hint are static in the current
Commands Interface and update after Profile restart.

Locale reads do not alter recorder state.

### Dictionary Interface

All user-facing text is addressed by stable semantic keys. Chinese and English
dictionaries must have identical key sets at compile time and in tests.

The localized surface includes:

- `/flight` description and input hint;
- usage and validation errors;
- empty, missing, ambiguous, and evicted-record errors;
- Record, List, Diff, Health, Explain, and Stats titles;
- field labels;
- finite outcome, finish, correlation, omission, and explanation labels.

The following remain machine-stable and untranslated:

- command and subcommand tokens;
- Provider, Model, Tool, Prompt Section, Context, and Variable names;
- record IDs;
- protocol constants and field paths;
- numeric values and diff operators.

Missing translation keys are build failures. Runtime output must not expose a
key or mix fallback languages.

### Command Execution Flow

```text
resolve current Host locale
  -> read one Session Snapshot
  -> parse command
  -> filter, resolve, diff, explain, or aggregate in that revision
  -> format with the selected dictionary
  -> enforce the 4 KiB output bound
```

### List Filters

Extend the grammar without changing existing commands:

```text
/flight list [limit]
/flight list failed [limit]
/flight list slow [limit]
/flight list truncated [limit]
```

Rules:

- `failed`: `threw` or `incomplete`;
- `slow`: terminal `totalMs` at or above `slowTotalMs`;
- `truncated`: at least one positive omission counter;
- default limit: 10;
- explicit limit: integer from 1 through 20;
- every filter is restricted to the invoking Session.

Add two optional diagnostic thresholds:

```ts
{
  slowFirstChunkMs?: number // default: 1_000
  slowTotalMs?: number      // default: 2_000
}
```

Both must be finite positive safe integers in milliseconds.
`slowFirstChunkMs` is used by Explain and `slowTotalMs` is used by Explain and
the `slow` list filter. They affect only diagnosis and do not change records or
health.

### Explain

```text
/flight explain <id-prefix>
```

Explain is deterministic and rule-based. It consumes only the selected
existing record and reports confirmed observations plus bounded check
suggestions for:

- a request still running;
- incomplete stream termination;
- finite thrown-error classification;
- request or Prompt omissions;
- slow first Chunk or total duration;
- absent Prompt Assembly evidence.

It must not claim a root cause, call a model, retrieve content, or use raw
errors.

### Retained-Window Statistics

```text
/flight stats
```

Stats are computed over retained records for the invoking Session:

- retained record count;
- outcome distribution;
- success ratio: `finished / terminal`, unavailable when no terminal record
  exists;
- median and P95 first-Chunk and total duration;
- aggregate input and output Tokens when present;
- truncated-record count.

The heading explicitly says "retained window" in both languages. It must not
imply process-lifetime totals. Percentiles use the bounded retained array and
do not create another history store. Duration populations include only records
where the metric exists. Median is the average of the two middle values for an
even population. P95 uses nearest rank:
`sorted[ceil(0.95 * count) - 1]`. An empty population renders the localized
unavailable marker.

## Public Contract and SemVer

The v1 Reader protocol and record schema remain unchanged.

- New command behavior and optional plugin configuration are additive.
- Internal Module Interfaces are not exported.
- Client artifacts are packaged as DSH Client Half implementation details.
- If implementation discovers that locale access requires a public Reader
  change or a record field, the work stops for a separate protocol and SemVer
  review.

The intended release is 1.1.0 because it adds DSH compatibility automation,
new commands, configuration, and multilingual behavior.

## Error Handling

- Missing Settings: use Chinese without failing recorder startup.
- Invalid locale: use Chinese and do not persist a repaired value from Host.
- Initial Client synchronization failure: contain and log a finite
  locale-sync warning; diagnostics remain available in Chinese.
- Command parse failure: return localized usage.
- Missing or ambiguous ID: return a localized Session-scoped error.
- Empty metric population: render a localized unavailable marker rather than
  inventing zero.
- Compatibility failure: fail the relevant CI layer with no automatic support
  claim.

No error path may retain or display raw provider errors.

## Verification Strategy

### Focused TDD

Every behavior starts with a focused failing test. Tests then cover:

- Recorder State transaction invariants;
- Adapter event sequencing and downstream identity;
- one-Snapshot command execution;
- complete bilingual dictionary keys;
- locale normalization and Chinese fallback;
- one-time Client synchronization only when preference is absent;
- immediate output change after Host preference change;
- startup-time description and hint language;
- bilingual filters, Explain, Stats, errors, and 4 KiB bounds;
- Session isolation and privacy canaries in both languages.

### Complete Local Gate

```sh
pnpm test:coverage
pnpm typecheck
pnpm build
git diff --exit-code -- lib
pnpm exec publint
pnpm bench
```

Coverage remains 100 percent for statements, branches, functions, and lines.

### Distribution Gate

- Pack the artifact.
- Verify exact Host and Client artifact allowlists.
- Install it in a fresh consumer.
- Import root and invariant entries.
- Verify no install scripts.
- Verify Client Half metadata resolves only on the Web platform.

### DSH Integration Matrix

For the supported RC on Node 22.19 and Node 24:

- isolated npm installation;
- Profile composition;
- Web startup;
- initial browser `zh` and `en` detection synchronization;
- explicit preference preservation;
- runtime output switch;
- restart-time description switch;
- two Mock Agent Loop requests;
- all command paths;
- privacy scan;
- restart cleanup.

The newly discovered RC remains observational until explicitly adopted.

## Documentation

Update:

- both READMEs with bilingual runtime behavior and new commands;
- API documentation with unchanged Reader protocol;
- architecture documentation with the three deep Modules and minimal Client
  Half;
- privacy threat model with locale data flow and command persistence;
- compatibility documentation with the automated matrix;

- Changelog with factual release status only.

Chinese and English documentation must preserve identical commands, limits,

## Completion Criteria

The implementation is complete only when:

1. current-RC static, isolated, and real Agent Loop gates pass;
2. new-RC discovery reports without mutating the repository;
3. public v1 protocol, schema, Reader Interface, and privacy allowlist are
   unchanged;
4. recorder transactions and Harness knowledge have the specified locality;
5. `/flight` reads one atomic Snapshot per execution;
6. `zh` and `en` outputs are complete and language changes affect the next
   command;
7. initial browser locale synchronizes only when no explicit preference
   exists;
8. descriptions and hints use startup language and update after restart;
9. filters, Explain, and Stats remain bounded and Session-scoped;
10. `aborted` and `error` Finish failures retain no message, code, or request
    ID and appear as finite `threw:error` outcomes;
11. all automated, distribution, compatibility, Soak, benchmark, privacy, and
    cleanup gates pass.
